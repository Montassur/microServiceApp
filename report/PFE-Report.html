Introduction générale

L'évolution rapide du commerce électronique impose aux entreprises de disposer de plateformes logicielles à la fois robustes, évolutives et capables d'absorber des charges de trafic variables. Les architectures monolithiques traditionnelles, longtemps privilégiées pour leur simplicité de mise en œuvre, montrent leurs limites dès lors qu'il s'agit de faire évoluer indépendamment plusieurs domaines métiers, de déployer fréquemment de nouvelles fonctionnalités, ou de garantir une haute disponibilité.

Dans ce contexte, ce projet de fin d'études porte sur la conception, le développement et le déploiement d'une plateforme e-commerce complète en architecture microservices, avec une chaîne d'intégration et de livraison continues (CI/CD) entièrement automatisée selon les principes GitOps. Le système couvre l'ensemble du cycle de vie applicatif : du développement local à la mise en production sur un serveur dédié, en passant par les tests automatisés, la construction d'images Docker, et le déploiement déclaratif sur un cluster Kubernetes.

La problématique centrale traitée par ce projet est la suivante : comment construire et déployer une plateforme e-commerce moderne en respectant les bonnes pratiques DevOps actuelles (microservices, conteneurisation, orchestration, observabilité, infrastructure-as-code), tout en garantissant un cycle de livraison rapide, traçable et réversible ?

Les objectifs de ce rapport sont triples :

  • Présenter de manière exhaustive l'architecture technique de la plateforme et justifier les choix technologiques effectués ;
  • Détailler la stratégie de déploiement et le pipeline CI/CD mis en place ;
  • Démontrer la maîtrise des outils cloud-native modernes (Kubernetes, ArgoCD, Sealed Secrets, Prometheus, Grafana).

Le présent rapport est organisé en quatre chapitres. Le premier chapitre présente le contexte du stage et les enjeux du projet. Le deuxième chapitre détaille l'analyse fonctionnelle et la conception. Le troisième chapitre décrit l'implémentation et les choix techniques. Enfin, le quatrième chapitre aborde la validation et les tests effectués. Une conclusion générale dresse le bilan du travail et présente les perspectives d'amélioration.

1.2 Présentation du projet

1.2.1 Objectifs

Le projet, baptisé Ecommerce, vise à concevoir une plateforme e-commerce complète selon les standards modernes du développement cloud-native. Au-delà des aspects fonctionnels classiques d'un site marchand (catalogue produits, panier, commande, paiement, livraison), le projet met l'accent sur l'ingénierie de production : conteneurisation, orchestration, observabilité, automatisation du déploiement.

Les objectifs détaillés sont :

  • Implémenter une architecture orientée microservices découpée selon les domaines métier (Domain-Driven Design) ;
  • Mettre en œuvre une communication asynchrone événementielle entre services via un broker de messages ;
  • Construire un pipeline d'intégration continue automatisant les phases de qualité, de tests et de construction d'images ;
  • Déployer la plateforme sur un cluster Kubernetes en suivant les pratiques GitOps (le dépôt Git comme source de vérité) ;
  • Mettre en place une observabilité de production via collecte de métriques et tableaux de bord ;
  • Sécuriser l'ensemble de la chaîne via HTTPS, secrets chiffrés et bonnes pratiques d'isolation.

1.2.2 Périmètre fonctionnel

La plateforme couvre les fonctionnalités suivantes :

  • Authentification et gestion des utilisateurs : inscription, connexion, gestion des sessions, contrôle d'accès basé sur les rôles (RBAC) avec trois niveaux (user, admin, editor) ;
  • Catalogue produits : consultation, recherche full-text via RediSearch, recommandations, gestion des avis clients ;
  • Panier d'achat et liste de souhaits : stockage rapide en mémoire via Redis ;
  • Gestion des commandes et paiements : intégration Stripe, traitement des transactions selon le pattern Saga ;
  • Logistique : préparation des expéditions, suivi de livraison, gestion des coupons de réduction ;
  • Gestion des stocks : suivi temps-réel des quantités, alertes de seuil bas ;
  • Tableau de bord administrateur : gestion CRUD des produits, utilisateurs, commandes ;
  • Analyses et audit : journalisation des actions sensibles, métriques d'usage, exports.

1.2.3 Enjeux techniques

Plusieurs enjeux techniques structurants ont guidé la conception :

  • Scalabilité horizontale : chaque service doit pouvoir être répliqué indépendamment ;
  • Résilience : la défaillance d'un composant ne doit pas compromettre l'ensemble du système ;
  • Déploiement continu : tout changement de code validé doit pouvoir être déployé en production en moins de dix minutes ;
  • Sécurité : les données sensibles (mots de passe, jetons, clés de paiement) doivent être protégées de bout en bout ;
  • Traçabilité : chaque déploiement doit être réversible et associé à un commit Git précis.

1.3 Environnement de travail

Le projet a été mené selon une approche itérative et incrémentale, inspirée de la méthodologie Agile. Le développement s'est organisé en cycles courts, chaque itération aboutissant à un livrable fonctionnel testable. Le suivi de version a été assuré via Git avec un dépôt central hébergé sur GitHub (github.com/Montassur/microServiceApp).

Les outils utilisés pour la gestion et le développement comprennent :

  • Visual Studio Code comme environnement de développement intégré ;
  • Docker Desktop pour l'exécution locale des conteneurs ;
  • GitHub Actions pour l'intégration continue ;
  • ArgoCD pour le déploiement continu en mode GitOps ;
  • DBeaver pour l'administration des bases de données PostgreSQL ;
  • OpenLens / k9s pour l'exploration du cluster Kubernetes.

2.2 Architecture globale

L'architecture retenue est une architecture microservices à dix services, orchestrée derrière une passerelle Nginx. Les services backend communiquent de manière synchrone via HTTP REST pour les requêtes utilisateur, et de manière asynchrone via le broker RabbitMQ pour les événements métier.

L'organisation en couches est la suivante :

  • Couche présentation : deux applications React (storefront client et admin) servies par Nginx ;
  • Couche passerelle : un reverse-proxy Nginx (gateway) qui route les requêtes vers le bon service backend selon le préfixe d'URL (/api/auth, /api/products, etc.) ;
  • Couche métier : sept microservices Node.js Express, chacun gérant un domaine fonctionnel (authentification, catalogue, commandes, etc.) ;
  • Couche données : PostgreSQL pour les données persistantes, Redis pour le cache et le moteur de recherche, RabbitMQ pour la messagerie événementielle.

3.4 Fonctionnalités clés réalisées

3.4.1 Pipeline CI/CD GitOps

Le cœur du projet est la chaîne CI/CD entièrement automatisée définie dans .github/workflows/ci.yml. Le schéma suivant en décrit le flux complet :

Figure 3.4 — Pipeline CI/CD complet : du git push à la production

Les cinq étapes du pipeline CI/CD sont :

  1. Lint — exécution d'ESLint sur les 9 services applicatifs en parallèle ;
  2. Test — exécution de Jest sur les 7 services backend ;
  3. Build — construction Docker buildx et publication des 10 images sur GitHub Container Registry (GHCR), avec tags branch et sha-<commit> ;
  4. Validation Kubernetes — kubectl kustomize sur les overlays développement et production ;
  5. CD — Bump des tags — étape finale réécrivant infrastructure/k8s/overlays/production/kustomization.yaml avec le SHA du nouveau commit, puis poussant le changement avec le marqueur [skip ci].

3.4.2 Recherche avancée via RediSearch

Le service catalog utilise le module RediSearch de Redis Stack pour offrir une recherche full-text instantanée. À chaque création/modification d'un produit, un événement RabbitMQ déclenche la mise à jour de l'index (JSON.SET, FT.CREATE).

3.4.3 Observabilité — Prometheus et Grafana

Chaque service backend expose un endpoint /metrics au format Prometheus. Le scrapping est effectué toutes les 15 secondes. Trois tableaux de bord Grafana sont provisionnés automatiquement :

  • Ecommerce Microservices Overview : santé, CPU, mémoire, latence p95 par service ;
  • NodeJS Application Dashboard : heap, event loop, garbage collector ;
  • RabbitMQ Overview : files, consommateurs, taux de messages.

3.5 Sécurité et authentification

La sécurité a été abordée à plusieurs niveaux :

  • HTTPS systématique via certificats Let's Encrypt renouvelés automatiquement par Apache + certbot ;
  • JWT signés avec une clé aléatoire de 256 bits ;
  • Chiffrement des secrets en dépôt Git via Sealed Secrets : seul le cluster possède la clé privée de déchiffrement ;
  • Isolation réseau : NGINX Ingress n'expose que les services frontaux ;
  • Rate limiting Nginx (zones limit_req_zone) contre les abus ;
  • En-têtes de sécurité : X-Frame-Options, X-Content-Type-Options, Content-Security-Policy ;
  • Hashage bcrypt à 10 itérations pour les mots de passe.

Chapitre 4 — Tests et validation

4.1 Stratégie de tests

4.1.1 Qualité statique (Lint)

L'outil ESLint est exécuté automatiquement à chaque commit sur les 9 services disposant de code JavaScript/JSX. La configuration applique les règles strictes pour React 19 (react-hooks/purity, react-hooks/exhaustive-deps, react-refresh/only-export-components).

4.1.2 Tests unitaires

Le framework Jest est configuré sur les 7 services backend. Les scripts npm test sont prêts à recevoir des suites de tests dans le dossier __tests__/. À l'heure actuelle, la suite est volontairement vide (--passWithNoTests activé pour ne pas bloquer le CI), en attente d'évolution.

4.1.3 Tests d'intégration des manifestes Kubernetes

Le pipeline CI inclut une étape k8s-validate qui exécute kubectl kustomize sur les overlays développement et production, garantissant la validité syntaxique des manifestes et la résolution de toutes les références (ConfigMap, Secret, Service).

4.1.4 Tests de bout en bout (manuel)

La recette fonctionnelle a été conduite manuellement sur les flux utilisateurs critiques : inscription, connexion, navigation produit, ajout au panier, passage de commande, consultation des commandes par l'administrateur.

Conclusion générale

Bilan du travail réalisé

Ce projet de fin d'études a permis de concevoir, développer et déployer une plateforme e-commerce complète en architecture microservices mise en production sur un cluster Kubernetes. Le système comprend dix microservices spécialisés, une chaîne d'intégration et de livraison continues entièrement automatisée selon les principes GitOps, ainsi qu'une couche d'observabilité opérationnelle (Prometheus, Grafana).

L'ensemble est accessible publiquement via six sous-domaines sécurisés en HTTPS, et tout changement de code validé est déployé automatiquement en production en moins de dix minutes. La séparation stricte entre l'environnement de développement local (Docker Compose) et la production (Kubernetes) garantit la sécurité de la chaîne de livraison.

Compétences acquises

Compétences techniques :

  • Maîtrise de Node.js, Express et React 19 ;
  • Conception et implémentation d'une architecture microservices ;
  • Communication événementielle via RabbitMQ ;
  • Conteneurisation Docker et orchestration Kubernetes (k3s) ;
  • Mise en œuvre du modèle GitOps avec ArgoCD ;
  • Sécurisation des secrets via Sealed Secrets ;
  • Mise en place d'une chaîne CI/CD GitHub Actions ;
  • Observabilité avec Prometheus et Grafana.

Compétences transversales :

  • Diagnostic et résolution méthodique de problèmes complexes (lecture de logs, traçage inter-services) ;
  • Documentation technique détaillée (PROJECT_GUIDE.md, RABBITMQ_EVENTS.md, SESSION_LOG.md) ;
  • Capacité à raisonner sur des systèmes distribués.

Conflit de ports entre Apache (sites tiers) et NGINX IngressMise en place de NGINX Ingress en NodePort 30080 et configuration d'Apache en reverse-proxy SSL
Schéma de base incohérent (colonne name manquante)Ajout d'un ALTER TABLE ... ADD COLUMN IF NOT EXISTS idempotent
Cycle de dépendances Compose (frontend/admin/gateway)Utilisation du résolveur DNS Docker (127.0.0.11) avec variables Nginx
Identifiants RabbitMQ incohérents K8s/NodeConstruction de l'URL AMQP via substitution $(VAR) Kubernetes

Perspectives et améliorations futures

  • Suite de tests unitaires complète : ajouter au moins un test de fumée par service (Jest + supertest) ;
  • Tests de charge : intégrer k6 ou JMeter pour valider la tenue en charge ;
  • Documentation OpenAPI/Swagger pour chaque API ;
  • Outil de migration de schéma : intégrer node-pg-migrate ou Prisma Migrate ;
  • Tracing distribué : déployer Jaeger ou Tempo avec instrumentation OpenTelemetry ;
  • Sauvegardes automatisées : CronJob pg_dump → S3 ;
  • Mode multi-nœuds : étendre k3s sur un second nœud pour la vraie HA ;
  • CDN devant la passerelle : Cloudflare pour DDoS et cache statique.

Ce projet constitue une base solide et professionnelle, démontrant la maîtrise complète d'une chaîne de production cloud-native moderne — depuis la conception orientée domaines jusqu'au déploiement automatisé sur infrastructure réelle.

Annexe A — Configuration ArgoCD

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: ecommerce-production
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/Montassur/microServiceApp.git
    targetRevision: main
    path: infrastructure/k8s/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: ecommerce-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Annexe B — Glossaire technique

TermeDéfinition
GitOpsMéthodologie où le dépôt Git est la source de vérité unique pour l'état souhaité du système. Tout changement passe par un commit.
KustomizeOutil natif Kubernetes permettant de générer des variantes de manifestes via overlays sans templating.
ArgoCDContrôleur Kubernetes qui synchronise continuellement l'état du cluster avec le dépôt Git de référence.
SagaPattern de transaction distribuée par enchaînement d'événements compensables.
Sealed SecretsContrôleur qui déchiffre dans le cluster des secrets chiffrés versionnés en Git.
IngressRessource Kubernetes qui expose des services HTTP/HTTPS depuis l'extérieur du cluster.
RBACRole-Based Access Control : contrôle d'accès basé sur les rôles assignés aux utilisateurs.
JWTJSON Web Token : format de jeton signé pour l'authentification stateless.
k3sDistribution Kubernetes légère certifiée CNCF, conçue pour les déploiements edge et single-node.
GHCRGitHub Container Registry : registre d'images Docker hébergé par GitHub.
PodPlus petite unité déployable dans Kubernetes : regroupement de conteneurs partageant le réseau.
DeploymentRessource Kubernetes qui gère le cycle de vie des Pods (mise à l'échelle, mise à jour progressive).
StatefulSetVariante de Deployment pour les applications avec état (base de données, par exemple).
